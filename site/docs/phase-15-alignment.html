Phase 15 coverage and alignment

Python SDK v0.13.2 is published on PyPI and GitHub Releases; see the release verification record. Python 3.10+ uses an explicitly installed matching CLI. No binary is installed or downloaded automatically.

Phase 14's alignment audit remains authoritative for its historical implementation and publication. No physical edit to every older example is needed: existing configurations and health semantics are consumed unchanged and are tested against released/current/released binaries.

Later phases

Phase 16 should reuse the subprocess/version/error contract and synchronized publication model. Phases 17–19 remain Go adapter expansion; listing a target type in Python does not implement it. Phase 20 can consume sync/async reports; Python reference middleware does not require the SDK. Phase 21 can use report exit codes and reuse the new package/compatibility CI. Phase 22 may consume structured reports without introducing telemetry in this SDK. Phase 23 still requires third-party adapter isolation rather than loading Python plugins in process. Phase 24 should cover SDK round-trips and schema conformance. Phase 25 must keep product/framework interoperability distinct from SDK fixture coverage. Phase 26 retains scoped authorization, external audit, native signing, broader fault/resource tests and Windows descendant lifecycle controls.

Validation and release acceptance

Run repository Go/Python/documentation checks, strict Helm lint and Kubernetes runtime scenarios, plus the dedicated installed-wheel CI matrix. Release builds must verify SDK metadata and vendored schema versions; the wheel rebuilt from the sdist must install independently. Post-publication acceptance includes GitHub signatures/checksums, archive contents and Linux behavior, PyPI hashes, attestations, clean-environment installation and exact-version CLI execution. Do not mark publication complete until those external checks pass.

Publication infrastructure recovery

The PyPA v1.13.0 annotated tag object differs from its commit SHA; Docker action images use the commit SHA. The workflow now pins the verified commit image. Publication-only recovery verifies existing draft assets, their source-bound signatures/checksums, OCI blobs and image identities before reusing the original Python files. No SDK, CLI, chart or contract changes are introduced; existing software tags and versioned packages remain immutable. The protected main branch is allowed by the PyPI deployment environment for explicit manual recovery. Future distributions should reuse these verification gates.
